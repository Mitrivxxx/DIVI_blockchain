# Sprint 1 — powrót do projektu + fundament pod „LinkedIn + Web3”

**Cel sprintu:** odświeżyć kontekst, naprawić krytyczne dziury (role issuer, auth na upload, sync DB↔chain), dorzucić 1–2 features zbliżające produkt do tematu pracy i wzmocnić wiarygodność warstwy blockchain (revoke + testy).

**Priorytet:** backend + blockchain. Frontend tylko jeśli blokuje demo.

**Kontekst tematu:** profil zawodowy z dokumentami (dyplom itd.) wystawionymi przez zweryfikowaną instytucję; rekruter widzi profil i ma pewność autentyczności dzięki hashowi w blockchainie + IPFS.

**Stan dziś (skrót):**

- Działa: auth (email / Web3 / Google), upload PDF → SHA-256 → Pinata → `issueDocument`, weryfikacja plikiem, lista po owner address, wnioski issuer (approve → `addIssuer`).
- Brakuje: publiczny profil + publikacja docs, tabela dokumentów w Postgres, revoke, testy kontraktu, spójne role issuer, auth na upload.

Szacowany zakres: **~1–2 tygodnie** (wybierz P0 + tyle P1 ile zmieścisz).

## Backlog — priorytety

### P0 — must (fundament bezpieczeństwa + spójność)

#### B1. Ujednolicić role issuer on-chain + w backendzie — DONE

Role: owner / admin / issuer / user. Jeden mapping `authorizedIssuers`; wnioski off-chain; approve (admin|owner) → `addIssuer` + DB role issuer. `IsIssuerAsync` → `authorizedIssuers`. Owner zarządza adminami (`/api/admins`). **Wymaga redeploy kontraktu** + update adresu w `.env`.

---

#### B2. Sync roli issuer w bazie + auth na upload

**Problem:** approve woła `addIssuer` na chain, ale **nie** ustawia `Member.MemberRoleId = issuer`. Upload **nie ma** `[Authorize(Roles = "issuer")]`.

**Zadania:**

- [ ] Po approve: znaleźć `Member` po `EthereumAddress` → `MemberRoleId = 2` (issuer)
- [ ] Po reject: opcjonalnie log / reason
- [ ] `POST /api/documents/upload-document` → `[Authorize(Roles = "issuer")]`
- [ ] Sprawdzić claimy JWT (czy po zmianie roli trzeba re-login / refresh)

**DoD:** zwykły user nie może uploadować; issuer po approve + nowym tokenie może.

---

#### B3. Quick wins / dług techniczny — DONE

- Nonce config w `OnModelCreating` jako sibling (nie zagnieżdżony)
- `Controllers/UserRoleController.cs` (rename)
- Auth Web3 verify + Issuer → Serilog
- Unique index `IX_Members_Email` + register `409` przy duplikacie (email lowercase)

---

### P1 — features pod temat pracy (tu jest „LinkedIn + Web3”)

#### F1. Persystencja dokumentów w PostgreSQL po issue — DONE

Tabela `Documents` (Hash PK + Cid, Issuer/Owner, IssuedByMemberId, TxHash, BlockNumber, Status…). Zapis po issue; listy `owner` / `issuer` / `issued-by-me` z DB; verify bierze metadane z DB (event-scan tylko fallback).

---

#### F2. Revoke dokumentu (kontrakt + API) — DONE

`DocumentStatus.Revoked`, `revokeDocument` + event; `DELETE /api/documents/{hash}/revoke`; DB Status=2; verify: `IsAuthentic` / `IsRevoked` / `Status`. Kontrakt: `0x6e1447b7756802eaA44e70ca32d1E9e9c13E5252`.

---

#### F3. Fundament publicznego profilu (minimum pod demo)

**Problem:** profil jest tylko prywatny (`[Authorize]`); brak „rekruter otwiera profil i widzi zweryfikowane docs”.

**Zadania:**

- [ ] Publiczny endpoint np. `GET /api/profiles/{ethereumAddress}` (bez auth) → bezpieczne pola (imię, bio, avatar) + **opublikowane** dokumenty
- [ ] Flaga publikacji: `IsPublicOnProfile` na `Document` **lub** tabela `ProfilePublication` (MemberId, DocumentHash, Title, SortOrder)
- [ ] `POST /api/profile/documents/{hash}/publish` + `unpublish` (tylko owner)
- [ ] DTO bez email/haseł/wewnętrznych ID

**DoD:** znając adres ETH, anonimowy klient dostaje profil + listę opublikowanych docs z hashem / typem / issuerem / datą (link do verify).

> Frontend w S1: opcjonalnie surowy podgląd; pełny UI profilu publicznego może iść do S2.

---

#### F4. Bogatsza weryfikacja (API)

**Problem:** `DocumentVerificationResultDto` nie zwraca issuer / CID / type — rekruter widzi mało.

**Zadania:**

- [ ] Po `verifyDocument` + `getDocument` zwrócić: issuer, owner, cid, type, status, txHash, block, timestamp, explorer URL
- [ ] (Nice) `POST /api/documents/verify-hash` — weryfikacja samym hashem (bez uploadu PDF) pod privacy / client-side hash

**DoD:** response verify wystarczy do „raportu autentyczności” w UI / PDF później.

---

### P2 — jakość blockchain / praca dyplomowa (rób jeśli P0+P1 idą gładko)

#### C1. Testy Hardhat dla `DocumentIssuer`

- [ ] Suite: issue happy-path, duplicate reject, unauthorized issue, add/remove issuer, revoke, `getDocumentsByOwner`
- [ ] Uruchamiane lokalnie (`npx hardhat test`)

**DoD:** zielone testy; materiał pod rozdział „testy funkcjonalne” w pracy.

---

#### C2. Eventy ról + deploy polish — DONE

Eventy już w kontrakcie (`IssuerAdded`/`Removed`, `DocumentRevoked`, …). Jeden `scripts/deploy.js` (`npm run deploy:local|sepolia`); usunięty Counter + `deploySepolia.js`; README DIVI + Ignition `DocumentIssuer`.

---

#### C3. Audit / security log (szkic pod „analizę bezpieczeństwa”)

- [ ] Tabela `SecurityEvent` / `AuditLog`: timestamp, IP, userId?, path, outcome, reason
- [ ] Logować: failed auth, unauthorized upload, verify attempts (opcjonalnie)

**DoD:** kilka typów zdarzeń zapisuje się; da się pokazać w pracy jako „dziennik bezpieczeństwa”.

## Poza sprintem 1 (backlog pomysłów na później)

Trzymaj w głowie, ale **nie** pchaj do S1:

| Pomysł | Dlaczego później |
|--------|------------------|
| Pełny UI publicznego profilu (LinkedIn-like) | zależy od F3 |
| Batch issue dyplomów | po revoke + testach |
| Metadata instytucji on-chain | nice-to-have |
| Subgraph / indexer eventów | skalowanie |
| EIP-712 issue bez hot-wallet backendu | duża zmiana architektury |
| Upgradeability (UUPS) | świadoma decyzja „immutable registry” też OK w pracy |
| Raport PDF z weryfikacji | po F4 |
| Notyfikacje approve/reject | UX, nie core |
| Avatar upload | kosmetyka |
| Rate limiting auth/verify | hardening prod |
| Unpin Pinata przy fail chain | reliability |
| Client-side hash only (plik nie idzie na serwer) | privacy story — po F4 |
